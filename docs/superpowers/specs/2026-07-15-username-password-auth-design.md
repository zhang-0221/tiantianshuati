# 用户名密码账号体系设计

## 目标

将注册与登录改为纯“用户名 + 密码”流程，不再向用户收集邮箱、不发送验证码。学习资料、题库和进度继续按 Supabase 用户 ID 隔离并同步。

## 已考虑的方案

1. 保留邮箱验证并更换 SMTP 服务商：可提供邮箱找回，但仍依赖邮件投递。
2. 关闭邮箱验证、仍要求用户填写邮箱：实现简单，但用户仍需提供邮箱，不能满足纯账号密码体验。
3. 使用内部账号标识创建已确认用户：界面只展示用户名和密码；服务端基于规范化用户名生成不可投递的内部邮箱标识，并通过管理员接口创建已确认的 Supabase 用户。采用此方案。

## 用户体验

- 注册表单仅保留用户名和密码；移除邮箱输入框。
- 注册成功后直接建立会话并进入应用，无验证码页。
- 登录继续输入用户名和密码。
- 移除“重新发送验证码”和“忘记密码”入口及相关提示。
- 已有用户继续用原用户名和密码登录，现有云端数据不迁移、不丢失。
- 对于此前因邮件验证失败而未确认的既有账号，在首次输入正确密码登录时自动确认，无需再发送邮件。

## 服务端与数据

- `profiles.username` 继续作为全局唯一的登录名，规则保持为 3–24 位小写字母、数字或下划线。
- 注册接口在服务端生成 `用户名@users.tiantianshuati.invalid` 形式的内部标识；`.invalid` 为保留、不可投递域名，仅满足 Supabase 的邮箱型身份字段要求。
- 注册接口使用服务端 Supabase 管理员能力创建用户，并标记为已确认，避免任何邮件投递。
- 注册后由服务端以该内部标识与密码建立普通用户会话；前端只接收并保存该会话，不接触管理密钥。
- 登录接口沿用按用户名查询 `profiles` 后进行密码登录的现有路径。
- 保留 `profiles.email` 字段以兼容既有账号；新账号存储内部标识。不会向前端返回该字段。

## 边界与取舍

- 纯用户名密码账号没有已验证邮箱，因此不提供自助找回密码。
- 忘记密码时的处理方式为日后可增加管理员重置，或由用户主动绑定邮箱后启用找回；这不属于本次范围。
- 不修改现有资料、试卷、学习进度的同步与行级权限策略；它们继续以 `auth.uid()` 作为归属依据。
- 不依赖 QQ SMTP；现有 SMTP 配置可保留但不参与新注册流程。

## 错误处理与验证

- 用户名已被占用时显示明确提示，不透露其他账号信息。
- 用户名格式或密码长度不符合要求时在前端与服务端同时拒绝。
- 注册成功必须返回可用会话；若无法建立会话，前端显示失败并不写入本地登录状态。
- 自动化测试覆盖：注册请求不接受用户邮箱、内部标识生成、管理员创建参数、直接会话返回、登录兼容旧账号，以及验证/找回入口移除。
